1. Anthropic’s own account of two rejected designs for how Claude asks clarifying questions, and why Claude Code reads code with Grep instead of retrieval.

(single-source — vendor-primary)

Asking Claude for a plan and a set of clarifying questions about that plan in the same turn confused the model — it would drop options or abandon the plan’s structure entirely — so Anthropic split the two into separate turns. A persistent todo-list reminder had a similar problem: it made Claude treat its own plan as fixed rather than revisable once circumstances changed.

The same post explains why Claude Code’s tool is Grep, not retrieval-augmented generation: pre-fetching context for Claude, instead of letting it search for the context itself the way it already searches for everything else, didn’t match how the model actually works. Anyone designing an agent’s plan-display or retrieval layer now has a first-party counter-example to both defaults.

2. A field experiment in a real store: a retail AI agent that appears to catch attention and disappears to redirect it beats one that’s always visible or never there.

(single-source — peer-reviewed journal)

Researchers at Keio University deployed a mixed-reality retail agent under three conditions — timed appearance/disappearance, constantly present, and constantly absent — and measured actual purchase conversion. The timed condition beat the always-present one significantly (odds ratio 1.74, overall model p=.011).

For ambient and kiosk interfaces, this is a direct argument against the “always-on assistant” default: timed intermittency, not constant visibility, is the lever that moves behavior.

3. Showing an evaluator a metric’s full distribution — not a single aggregate score — helps them catch more flawed AI explanations.

(single-source — arXiv preprint)

A 16-person study found that people reviewing AI-generated explanations spotted significantly more real flaws when shown the spread behind an explanation-quality metric than when shown one number standing in for it (p=.04).

The effect is modest, but it’s an interface decision, not a modeling one: expose the distribution, don’t collapse it to a point estimate, when the reviewer’s job is finding what’s wrong.

4. Keep a failed tool call visible in the conversation — scrubbing it from history can make some models stop retrying altogether.

(single-source — arXiv preprint)

Testing recovery after a tool-call error, researchers found that opening a fresh user turn while keeping the failed exchange in context avoids a severe stopping failure specific to Llama model families when that exchange gets removed from history — a 14.2-point swing in explicit-error recovery for smaller models, 10.5 points for larger ones. The effect didn’t show up on a different benchmark at all — a model-family-dependent fix, not a universal rule.

A “clean up the history” edit that removes a visible failure can cost more in broken recovery than it saves in tokens.

5. Superhuman rebuilt its Docs AI on a separate, agent-shaped API instead of wrapping its existing human-facing API in MCP.

(single-source — vendor-primary)

Superhuman’s own writeup draws a clean line between an API “built for people” and one built for “agent ergonomics”: the new API moves whole pages as Markdown blocks so a single workflow doesn’t fan out into dozens of small calls, and its calls are synchronous so one action needs one request instead of a client-side polling loop.

The decision argues against the common shortcut of exposing an existing human-facing API to agents through an MCP wrapper, once the two usage patterns diverge this far. This is the fourth capped or near-capped item from this blog in recent weeks — a concentration pattern worth watching, not a reason to discount this post.

Yesterday’s dossier

Yesterday’s dossier re-read the Chatbot Arena “both are bad” vote-share study behind the previous digest’s #1 item against the full public battle log it cites, and the numbers reproduce exactly — sample counts, table rows, every printed month effect. But the headline rise is a staircase, not a smooth drift: 70% of votes sit in three flat plateaus with no detectable trend inside them, concentrated instead in a few steps lining up with model-version arrivals (gpt-4o, May 2024; chatgpt-4o-latest, Aug 2024) — controlling for those steps, the trend falls from +1.71 to +0.79 points a month.

The paper’s defense of a stable interface uses main-branch commit dates, but production ran ahead of main every time it was checkable; a direct test at the true dates still clears the leading rival explanation (a new UI button). The mechanism — rising judge standards reading as falling model quality — isn’t new; it matches established criterion-drift findings (Levari et al. 2018, NAEP scoring), which the lanes should cite rather than re-prove. Left open: whether the steps are ordinary resets at visible public launches, or tied to something else that happens to coincide with launches.
